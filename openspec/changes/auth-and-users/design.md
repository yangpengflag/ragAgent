## Context

动机见 `proposal.md`，需求契约见 `specs/identity/spec.md` 与 `specs/authentication/spec.md`。本文件只写「怎么做」。

现有可复用的地基（`project-scaffold` 已交付）：

- 配置层（pydantic-settings + 必填项 fail-fast）、统一错误信封（`error_code` 语义化 snake_case）、结构化日志与 `request_id`、`BoundedBase`（UUID v7 主键 / 创建更新时间 / 软删）、Alembic 迁移与测试库守卫
- `GET /api/v1/health` 已存在且必须保持**匿名可访问**（不受本次鉴权影响）

环境约束：单机本地部署，Redis（6379 容器）可用；无 GPU、内存紧张，故不引入重量级依赖。

> 前端相关决策（会话状态机、令牌存储位置、守卫形态）**不在本 change**，已随 `frontend-auth-wiring` 的 design.md 一同交付。

## Goals / Non-Goals

**Goals:**

- 用**最小依赖**实现「可撤销」的会话：访问令牌短时无状态，刷新令牌可轮换、可撤销
- 鉴权做成**可复用依赖**（当前账号 / 角色要求），后续每个业务接口只需声明依赖，不再各自解析令牌
- 权限模型留出扩展点：系统角色与将来的知识库级角色解耦
- 接口契约与安全语义在本 change 内被完整验证（含 Redis 故障时的两种失败方向）

**Non-Goals（设计层面的边界）:**

- 不做分布式会话/共享令牌状态（单实例足够；将来多实例时 Redis 已是现成载体）
- 不做令牌密钥轮换与多密钥并存（`kid` 机制）
- 不为限流引入通用中间件框架（单场景，直接实现更简单）
- 不实现任何前端代码（见 `frontend-auth-wiring`）

## Decisions

### D1. 令牌形态：无状态访问令牌 + 有状态刷新令牌

**选择**：访问令牌 = 签名 JWT（短时，默认 15 分钟），刷新令牌 = 签名 JWT + Redis 撤销名单，且每次刷新**轮换**（旧令牌立即拉黑）。

**备选**：① 全无状态（刷新不可撤销，登出形同虚设）；② 纯 Cookie 会话（服务端存会话状态）——与「前端持有 Bearer 访问令牌」的请求层契约冲突，且多端更麻烦。

**理由**：业务接口用无状态令牌校验（零存储查询、天然水平扩展），只有「刷新」这一低频路径访问 Redis。

### D2. 依赖选型修正：PyJWT + pwdlib[argon2]

**选择**：`PyJWT` 负责令牌签发/校验；`pwdlib[argon2]`（Argon2id）负责密码哈希。

**备选（均被否决）**：
- `python-jose`：3.3.0 及以下存在算法混淆漏洞（CVE-2024-33663 / CVE-2024-33664），维护活跃度低
- `passlib[bcrypt]`：最新版 1.7.4 发布于 2020 年，已事实停止维护；且与新版 `bcrypt` 存在兼容告警

**理由**：两者都是当前主流且维护活跃的选择；Argon2id 是 OWASP 推荐的密码哈希算法。

> ⚠️ 该决策**修订了 `openspec/project.md` 技术栈章节**的既定写法（原文写 `passlib[bcrypt]` + `python-jose`），本 change 需同步更新 project.md，避免"规格写了一版、代码跑另一版"。

### D3. 令牌放置：访问令牌走响应体，刷新令牌只走 HttpOnly Cookie

**选择**：登录/刷新响应体返回访问令牌；刷新令牌仅以 `Set-Cookie` 下发，属性 `HttpOnly` + `SameSite=Lax` + `Path=/api/v1/auth/refresh`，`Secure` 由配置决定（本地 http 关闭、生产必须开启）。

**备选**：刷新令牌也放响应体由客户端自行保存——与 spec 中「刷新令牌只从 Cookie 读取」的要求冲突，且长期凭据会落到脚本可读的位置。

**理由**：刷新令牌是长期凭据，必须在服务端侧就限定其传递通道；本 change 只负责把通道定死，前端如何配合是 `frontend-auth-wiring` 的事。

### D4. 撤销用黑名单 + 轮换

**选择**：刷新令牌载荷含 `jti`。刷新时签发新 `jti`、把旧 `jti` 写入 Redis 撤销名单（`SETEX`，TTL = 旧令牌剩余寿命）；登出把当前 `jti` 写入名单。校验刷新令牌时必须同时满足「签名有效」「未过期」「`jti` 不在名单」。

**备选**：白名单（登录时把 `jti` 写入 Redis，校验时必须存在）——需要保留全量会话状态，且 Redis 丢失即全员登出。黑名单状态更小、Redis 抖动时影响更可控。

**代价**：黑名单依赖「旧令牌必然被拉黑」，若拉黑写入失败会导致旧令牌仍可用——因此**刷新流程中拉黑失败必须整体失败**（fail-closed，见 D9）。

### D5. 刷新接口的 CSRF 防护

**选择**：三层——① 刷新令牌用 `SameSite=Lax`（跨站 POST 不带 Cookie）；② 刷新接口只从 Cookie 读取，请求体中的刷新令牌一律忽略；③ 校验请求的 `Origin`（缺失时退化为 `Referer`）属于配置的允许来源，否则 403。

**理由**：刷新是「无请求体、仅靠 Cookie 生效」的写操作，是 CSRF 的典型目标；仅靠 `SameSite` 在旧浏览器上不够。

### D6. 鉴权依赖每请求校验账号当前状态

**选择**：`get_current_user` 校验签名与过期后，**必须查库**确认账号存在且启用（软删与停用立即生效）。

**备选**：纯无状态（只信令牌声明）——停用账号最长仍可操作 15 分钟（访问令牌寿命）。

**理由**：企业内部系统的「停用/删除立即生效」比省一次主键查询更重要；单实例本地部署下开销可忽略。若将来成为热点，加 5 秒 TTL 的账号缓存即可（记入残风险）。

### D7. 角色模型分层：本次只落系统角色

**选择**：`system_role ∈ {ADMIN, MEMBER}`；`require_role(...)` 依赖按「所需角色集合」参数化，将来知识库级四档角色（KB_ADMIN / EDITOR / VIEWER）作为**另一层**校验接入，不改骨架。

**理由**：库级 ACL 的判定必须依赖「知识库」实体与「成员授权」表，属于 `knowledge-base-crud` 的范畴；此处提前实现只会返工。

### D8. 密码策略

**选择**：长度 12–128、不得与用户名相同；哈希使用 Argon2id 的库默认参数（可后续调优）；校验失败返回 422 并指明规则。

**备选**：再加「大小写+数字+符号」复杂度要求——已被现代实践反对（促使用户弱化记忆模式），长度下限更有效。

**取舍**：不做密码历史与弱口令字典校验（YAGNI，记入残风险）。

### D9. Redis 不可用时的取舍：撤销 fail-closed、限流 fail-open

**选择**：
- **刷新 / 登出**：Redis 操作失败时 **拒绝**该操作（503 `upstream_unavailable`）。撤销能力不可用时不发放新令牌，宁可让用户重新登录。
- **登录失败限流**：Redis 不可用时 **放行**（记录告警日志），不因限流组件故障阻断所有人登录。

**理由**：两者失败方向相反——撤销失效是安全问题（必须保守），限流失效是可用性问题（不应阻断业务）。这是本设计里唯一「同一依赖、两种失败方向」的地方，实现与测试必须显式区分。

### D10. 初始管理员引导放在启动流程

**选择**：应用 `lifespan` 启动阶段检查账号表是否为空；空表且配置了初始管理员用户名与密码时创建之，日志只记用户名不记密码；表非空则忽略配置。

**备选**：CLI 命令（`python -m app.cli create-admin`）——不在启动路径写凭据，但本地开发摩擦大且需额外文档。

**理由**：本地单机部署下「配好 `.env` 就能用」价值更高；CLI 将来可作为补充手段加入，不影响本设计。

### D11. 认证实现留抽象接口

**选择**：`AuthProvider` 协议（`authenticate(username, password) -> Account | None`），本 change 提供基于数据库 + Argon2 的本地实现；将来接 LDAP / OAuth2 只需新增实现。

**理由**：`project.md` 已明确「预留 AuthProvider 抽象」，且该抽象只此一处、成本极低。

### D12. 跨源携带凭据：必须显式开启且来源不得通配

**选择**：CORS 中间件开启 `allow_credentials=True`，来源**只能**是配置白名单中的具体源（不得为 `*`），与既有「非 debug 环境下拒绝通配符来源」的守卫一致。

**理由**：开发期前端在 `5173`、后端在 `8000`，二者**不同源**。浏览器在跨源请求中默认不发送也不接受 Cookie；不开启凭据支持时，登录响应里的 `Set-Cookie` 会被丢弃、刷新请求也带不上 Cookie——接口"看起来实现了"，但从浏览器调用必然失败。此外，规范禁止 `Allow-Credentials: true` 与 `Allow-Origin: *` 同时出现。

> 这是本 change 里唯一"因为前端形态而必须由后端调整"的地方，但它属于**后端的对外契约**（Cookie 能否生效），因此放在本 change 而不是前端 change 中。

### D13. 数据模型与迁移

**选择**：新增 `users` 表（`username` 唯一索引 + 软删标记），沿用 `BoundedBase` 的公共字段；迁移只建表，无数据迁移。回滚即 `drop table`。

`username` 唯一性由**数据库唯一约束**保证（并发创建同名账号时靠约束而非「先查后插」），业务层把约束冲突转换为 409。

## Risks / Trade-offs

- **签名密钥管理** → `APP_SECRET_KEY` 缺失或长度不足时**启动失败**（fail-fast）；密钥轮换不支持，泄漏只能全员换密钥（记入残风险）
- **每请求一次用户查询**（D6）→ 当前规模可忽略；若成为热点，加短 TTL 缓存（需接受「停用延迟 ≤ TTL」）
- **Redis 故障的两面性**（D9）→ 已按「安全 fail-closed / 可用性 fail-open」区分；测试必须覆盖两条分支
- **本地 http 环境下 Cookie 无法 `Secure`** → `Secure` 由配置驱动，默认本地关闭；`.env.example` 明确注释生产必须开启
- **黑名单依赖轮换写入成功**（D4）→ 拉黑失败即整体失败，不允许「发了新令牌但旧令牌未失效」
- **限流按用户名 + 来源地址** → 分布式/多 IP 慢速爆破不在防护范围（记入残风险）
- **接口在 `frontend-auth-wiring` 之前无人调用** → 属预期：本 change 的验收靠接口级测试与真实 HTTP 联调，不依赖 UI

## Migration Plan

实现顺序（也是 tasks 的顺序）：

1. 配置项、依赖与规格同步（含 `project.md` 技术栈修订）
2. `Account` 模型 + Alembic 迁移
3. 密码与令牌原语（纯函数，可单测）
4. 认证服务（登录、刷新、登出、限流、初始管理员引导）
5. 鉴权依赖 + `auth` / `users` 路由 + 错误语义（401 / 403 / 409 / 422 / 429 / 503）
6. 真实 HTTP 联调与收尾

**回滚**：本 change 不影响既有接口（`/health` 保持匿名）。若不启用，只需不配置初始管理员、不调用新接口；数据库侧 `alembic downgrade` 删除 `users` 表。
