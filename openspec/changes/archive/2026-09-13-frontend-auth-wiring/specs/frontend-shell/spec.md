## MODIFIED Requirements

### Requirement: API 客户端统一处理基址、鉴权与错误

系统 SHALL 提供统一的 API 客户端：基址取自 `VITE_API_BASE_URL`（默认 `http://localhost:8000`）；请求 MUST 自动携带 Bearer 访问令牌（若已持有）；当服务端返回 401 时，客户端 MUST 尝试刷新令牌并重放原请求**一次**，刷新失败则跳转登录；所有错误 MUST 归一化为 `ApiError { request_id, error_code, message, details? }` 结构。

字段名 MUST 与后端 JSON 保持一致（snake_case），不得引入大小写转换层。

刷新令牌 MUST 只通过 `HttpOnly` Cookie 传递：前端 MUST NOT 读取、存储或以脚本可访问的方式持有刷新令牌，刷新请求 MUST 以携带凭据的方式发送。

**认证端点必须豁免刷新重放**：登录、刷新、登出三个端点自身返回 401 时，客户端 MUST NOT 触发令牌刷新、MUST NOT 重放该请求（否则刷新失败的 401 会递归触发刷新，导致请求自等待）。

#### Scenario: 注入访问令牌

- **WHEN** 已持有访问令牌时发起请求
- **THEN** 请求头中包含 `Authorization: Bearer <token>`

#### Scenario: 401 后刷新并重放

- **WHEN** 请求返回 401 且刷新令牌有效
- **THEN** 客户端自动刷新令牌并重放原请求一次，调用方得到重放后的成功结果

#### Scenario: 刷新失败跳转登录

- **WHEN** 请求返回 401 且刷新令牌无效
- **THEN** 客户端跳转登录页，且不重复发起原请求

#### Scenario: 错误归一化

- **WHEN** 服务端返回错误响应
- **THEN** 调用方收到的错误对象包含 `request_id`、`error_code`、`message` 字段，字段名与后端一致

#### Scenario: 前端不持有刷新令牌

- **WHEN** 客户端发起刷新
- **THEN** 刷新请求以携带凭据的方式发送，且前端代码中不存在读取或写入刷新令牌的路径

#### Scenario: 认证端点不触发刷新重放

- **WHEN** 登录、刷新或登出接口自身返回 401
- **THEN** 客户端不触发令牌刷新、不重放该请求，直接把失败交给调用方处理

#### Scenario: 刷新失败后会话状态变为匿名

- **WHEN** 刷新令牌失效导致刷新失败
- **THEN** 会话状态变为匿名（不仅是页面跳转），且后续业务请求不再携带旧的访问令牌

## ADDED Requirements

### Requirement: 应用启动时恢复登录会话

系统 SHALL 在应用启动时尝试恢复既有登录会话：若存在有效的刷新令牌则换取访问令牌并加载当前账号，否则视为未登录。恢复过程中 MUST NOT 渲染受保护页面内容，也 MUST NOT 出现「先闪现受保护内容再跳走」的情况。

#### Scenario: 存在有效会话时直接进入应用

- **WHEN** 应用启动且刷新令牌有效
- **THEN** 完成会话恢复，进入目标页面，并在外壳中展示当前账号

#### Scenario: 无有效会话时进入登录页

- **WHEN** 应用启动且无刷新令牌或刷新失败
- **THEN** 视为未登录，跳转登录页，不渲染受保护内容

#### Scenario: 会话恢复期间呈现加载态

- **WHEN** 应用启动且会话恢复尚未完成
- **THEN** 呈现明确的加载态，不渲染受保护页面内容，也不呈现「未登录」这类可能误导的界面

#### Scenario: 引导期间服务不可用

- **WHEN** 会话恢复因网络错误或服务端故障失败（区别于刷新令牌无效）
- **THEN** 展示可重试的失败提示与重试入口，而不是静默地把用户当作未登录

#### Scenario: 刷新成功但当前账号查询被拒

- **WHEN** 刷新令牌换取访问令牌成功，但随后的当前账号查询返回 401
- **THEN** 视为未登录（会话置为匿名）并跳转登录页，不进入已登录态

### Requirement: 受保护路由要求登录并可回到原目标

系统 SHALL 对受保护路由实施登录态校验：未登录访问受保护路由 MUST 跳转登录页，并保留原目标地址；登录成功后 MUST 返回原目标地址。登录页与系统状态页 MUST NOT 要求登录（后者是排障入口，未登录也应可访问）。

#### Scenario: 未登录访问受保护路由

- **WHEN** 未登录状态下访问受保护路由
- **THEN** 跳转登录页，且不渲染该路由内容

#### Scenario: 登录后回到原目标

- **WHEN** 未登录访问某受保护路由后完成登录
- **THEN** 自动返回该受保护路由

#### Scenario: 登录页与系统状态页不需登录即可访问

- **WHEN** 未登录状态下访问登录页或系统状态页
- **THEN** 正常渲染该页面内容

### Requirement: 登录页覆盖提交中、失败与成功

系统 SHALL 提供登录页：用户名与密码表单、提交中状态、失败提示与成功后进入应用。失败提示 MUST 可读且 MUST NOT 泄露账号是否存在；提交中 MUST 禁止重复提交。

#### Scenario: 登录成功

- **WHEN** 提交正确的用户名与密码
- **THEN** 进入应用（回到原目标或默认页），并展示当前账号

#### Scenario: 凭据错误

- **WHEN** 提交错误的凭据
- **THEN** 展示可读的错误提示，表单可再次提交，且提示不区分用户名是否存在

#### Scenario: 提交中禁止重复提交

- **WHEN** 登录请求进行中
- **THEN** 提交控件处于不可重复提交的状态并给出加载反馈

#### Scenario: 网络或服务不可用

- **WHEN** 登录请求因网络错误或服务端故障失败
- **THEN** 展示可读的错误描述，并可重试

#### Scenario: 登录被限流

- **WHEN** 登录请求返回 429 且 `error_code` 为 `rate_limited`
- **THEN** 展示「尝试过于频繁，请稍后再试」这类可读提示，且表单仍可再次提交

### Requirement: 已登录时可查看当前账号并登出

系统 SHALL 在已登录时于应用外壳展示当前账号标识，并提供登出入口。登出 MUST 清除本地访问令牌、通知服务端撤销刷新令牌，并在完成后回到登录页；登出后 MUST NOT 再以旧令牌发起业务请求。

#### Scenario: 展示当前账号

- **WHEN** 已登录并进入应用
- **THEN** 外壳中可见当前账号的用户名或显示名

#### Scenario: 登出后回到登录页

- **WHEN** 已登录用户触发登出
- **THEN** 会话被清除并跳转登录页

#### Scenario: 登出后不再携带旧令牌

- **WHEN** 登出完成后发起任意受保护请求
- **THEN** 请求不携带旧的访问令牌，且被引导回登录页

#### Scenario: 服务端撤销失败仍完成登出

- **WHEN** 触发登出但服务端登出接口失败或不可达
- **THEN** 本地会话仍被清除、用户回到登录页，并记录一条告警日志
